# 飞针机采集电脑状态上报设计

## 目标与范围

飞针机采集程序运行时，定期把所在 Windows 电脑的状态发送到当前配置的 QMS 服务器。QMS 按租户和电脑名保存最新状态，供现场确认采集电脑是否正常。用户选择只保存最新状态，不保留逐次采样历史。现有 TXT 扫描、设备遥测、待发队列和同步记录的语义保持不变。

实现涉及本仓库 `tools/flying-probe-collector` 和本机 QMS 仓库 `/Users/congee/project/qms` 的 `main` 分支。先部署 QMS 接收接口，再部署新版采集程序。

## 接口与数据

新增 `POST {QmsBaseUrl}/api/v1/gateway/host-status`，请求为单个 JSON 对象，字段如下：

| 字段 | 含义 |
| --- | --- |
| `hostName` | Windows 电脑名；租户内的最新状态键 |
| `sampledAt` | 带时区的采样时间；客户端发送 UTC `Z` 时间 |
| `cpuPercent` | CPU 使用率，0–100；首次采样缺少前一组 CPU 计数时可为 `null` |
| `memoryTotalBytes` / `memoryAvailableBytes` | 物理内存总量与可用量 |
| `systemDiskTotalBytes` / `systemDiskFreeBytes` | Windows 系统盘总量与可用量 |
| `uptimeSeconds` | 系统开机时长 |

沿用采集程序已有的 `X-Gateway-Token`、可选服务账号 `Authorization: Bearer ...`、`QmsBaseUrl` 和请求超时配置。QMS 在接收边界校验令牌、租户、电脑名、时间和数值范围；不接受可用量大于总量。服务端记录 `receivedAt`，用服务端接收时间判断数据新鲜度。对同一租户与电脑名使用唯一键更新一行最新状态，返回 `2xx` 表示写入成功。同名电脑在同一租户下会共享一行，因此部署时电脑名必须唯一。没有把电脑伪装成设备或复用设备映射；设备遥测端点会触发设备汇总和业务规则，不适合电脑状态。

QMS 提供需登录的 `GET /api/v1/gateway/host-status`，按当前租户返回最新状态及 `receivedAt`，方便现有 QMS 客户端或运维查询；本次不增加新的页面。未收到新请求的电脑可依据 `receivedAt` 识别为离线，不把离线状态写入表。

## 采集端行为

采集程序启动后立即采样一次，此后每 60 秒采样并上报。CPU 使用 Windows 系统计数的相邻采样差值，首次为 `null`；内存、系统盘和开机时长使用 Windows 系统 API 与 .NET Framework 现有能力，不引入外部依赖。上报任务与 TXT 扫描和文件事件发送任务独立运行，避免电脑状态请求超时拖慢文件同步。停止采集时停止新请求并等待当前请求在既有超时内结束。

电脑状态代表当前值，不进入 `pending-events.json`。非 `2xx`、重定向、网络错误或采样失败只记不含令牌的日志；下一轮发送新状态。采集程序不因状态上报失败退出，也不把该失败记成 TXT 文件同步失败。窗口和控制台版共享这项行为，不增加配置项或窗口控件。

## QMS 存储与安全

新增 Flyway 迁移，为最新状态建一张按 `(tenant_code, host_name)` 唯一的表，存放请求字段和 `received_at`；无采样历史与定时清理任务。新增接收和读取接口、最小服务与持久化代码。生产安全配置和现有网关租户过滤器覆盖新 POST 路径：仅有效网关令牌且租户有效时可写；携带服务账号 Bearer Token 时仍按 JWT 租户处理。GET 沿用登录用户的租户边界，不能跨租户读取。

## 验证与发布

- 采集端：本地 HTTP 测试校验路径、请求字段、鉴权头、60 秒调度、失败不阻断 TXT 同步和停止行为；Windows 实机核对 CPU、内存、磁盘与开机时长的数值范围。
- QMS：接口和服务测试校验字段约束、错误令牌、租户隔离、同一电脑更新而非新增、不同电脑互不覆盖，以及 GET 只返回当前租户数据。
- 更新采集程序、QMS 的接口说明和部署顺序；构建脚本纳入新增源文件。先升级 QMS 并执行迁移，再升级现场采集程序，核对 QMS 最新状态与现场电脑读数。

当前 macOS 开发环境没有 Windows .NET Framework 编译器或 Java 运行时；未能在本机执行的构建与实机指标核对需要明确报告，不能算作通过。
